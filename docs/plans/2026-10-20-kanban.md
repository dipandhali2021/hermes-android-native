# Kanban for Android — implementation plan

> **Status:** Awaiting approval. Do not implement until the design and this plan are
> approved.
>
> **Spec:** [`../specs/2026-10-20-kanban-design.md`](../specs/2026-10-20-kanban-design.md)  
> **Research:** [`../specs/2026-10-20-kanban-feature-inventory.md`](../specs/2026-10-20-kanban-feature-inventory.md)

## Goal

Replace the read-only Kanban panel with a full-screen, Material 3 Expressive
Kanban client over the existing Hermes WebUI `/api/kanban/*` bridge: a board with
status rail and pager, task detail with Overview/Activity/Runs, the workflow
verbs the bridge actually supports, create/edit, board management, live updates,
and a dispatcher sheet.

No backend changes. The WebUI bridge is the contract.

## Architecture

- **Wire** — `core/model/Kanban.kt` holds every DTO, all fields optional, with
  `@SerialName` for the bridge's snake_case.
- **Domain** — `domain/kanban/` holds pure logic: known statuses, labels, age and
  staleness formatting, client-side search, transitions/action matrix, create
  semantics, event summaries, activity merge, dispatcher summary. No Compose, no
  I/O.
- **Data** — `data/kanban/` holds `KanbanRepository` (interface) and
  `DefaultKanbanRepository` (Hilt). It owns the `/boards → /config → /board` load
  order, the create recipe, explicit-null PATCH construction, the task cache
  used by dependency chips, SSE parsing, and the polling fallback.
- **UI** — `ui/kanban/` holds one ViewModel + immutable UiState + effects channel
  per screen, plus composables. The board is a full-screen destination; the task
  detail, create/edit, log, new board, and board settings are destinations too.
- **Transport** — the existing `HermesApi` for HTTP; a new `RawSseClient` for the
  Kanban `hello`/`events` stream. The chat `SseClient` is untouched. A cloned
  dispatch client allows a 3-minute dispatcher call without changing the normal
  60-second API client.

The board is **board-scoped**: every task call carries `?board={slug}`. The task
routes carry the slug, so a server-side active-board switch elsewhere cannot
repoint a detail screen mid-edit.

## Tech stack

Kotlin 2.2.x, Compose BOM `2026.06.01`, material3 `1.4.0`, Hilt, Navigation
Compose, OkHttp + `okhttp-sse`, kotlinx.serialization, JUnit4, coroutines-test,
Turbine, `mockwebserver3`, Robolectric. No new runtime dependencies. No Kotlin,
Compose, material3, Coil, AGP, or SDK bumps (see `AGENTS.md`).

## Global constraints

- CI (`.github/workflows/android.yml`) is the source of truth. Local
  `./gradlew :app:testDebugUnitTest` is the fast path; a local full APK build is
  optional and disk-constrained.
- **No backend edits.** Never invent an endpoint; if the bridge lacks it, the
  feature is out of v1 (see the design §15).
- **No `GET /api/kanban/tasks`.** The old client used it, but it never existed as
  a list route. The board payload is the only list.
- **No browser headers.** Never send `Origin`, `Referer`, or `Sec-Fetch-*`.
  `hermes_session` is the cookie; there is no bearer token.
- **Optional wire fields.** Every DTO field has a default. Unknown keys are
  ignored; unknown statuses and unknown dispatcher buckets render generically.
- **Explicit nulls.** The app's `Json` has `explicitNulls = false`. Clearing
  `assignee`, `tenant`, or `body` must send an explicit JSON `null`, not omit the
  key. Use `JsonObject` for PATCH bodies.
- **Board-pinned task calls.** Every task, comment, link, log, and action call
  includes `?board={slug}`. The board switcher changes the server's active board;
  it never changes the slug of an open detail.
- **No offline queue.** Mutations fail fast with a message. There is no
  connectivity observer.
- **No drag-and-drop.** Status changes are explicit sheets. `running` is never a
  move target.
- **No review, attachments, hard delete, run-stop verb, or bulk multi-select** in
  v1. Archive-and-stop is the stop control.
- **Colors only from `MaterialTheme.colorScheme`.** The board palette lives in
  `ui/theme/Color.kt`; no `Color(0x...)` in a Kanban component.
- **Motion only from `ui/theme/Motion.kt`.** No raw `tween(...)`.
- **One immutable UiState + one effects `Channel` per screen.** Mutations set
  pending ids; the last server response wins via a load generation counter.
- **Tests first.** Each task lists the failing test before the implementation.
  The valuable tests use the server's real payload vocabulary, not invented
  shapes.

## Review focus

These are the five places an otherwise-correct implementation is most likely to
hurt a real person:

1. **Load order and filter defaults.** `/config` must load *before* the first
   `/board`; its `default_tenant` and `include_archived_by_default` must be
   visible active filters, not hidden defaults. A `/config` failure must degrade
   to defaults, while a `/board` failure must not. Test the request order and
   `changed:false`.
2. **Create status semantics.** Triage and Todo must both create with
   `triage: true` and never pass through Ready. Todo then PATCHes `todo`. Ready
   sends neither `triage` nor `status`; the server's parent gate decides. A naive
   create-Ready-then-patch is a dispatcher race and a dependency bypass.
3. **Explicit-null clearing.** The edit form must be able to remove an assignee,
   tenant, or body. With `explicitNulls = false`, an omitted key is a no-op and a
   user cannot clear a field. Test the raw JSON contains `"assignee": null`, not
   an absent key.
4. **Live updates.** A `changed:false` response has no columns. The SSE `events`
   frame is a cursor notification, not a board payload; it must trigger a full
   reload. Three SSE failures must fall back to polling while keeping the board
   usable, and a board switch must cancel the old stream before the new load.
5. **Mutation refusals and races.** A refused completion/block/archive returns an
   inconsistent 404/400/409. The app must show the server's words, restore an
   optimistic move, and offer the correct undo (Complete→Ready, Block→Unblock,
   Archive→previous legal status). Running cards must never offer Complete.

### Routes

```kotlin
object Routes {
    const val KANBAN = "kanban"
    fun kanbanTask(taskId: String, board: String, cursor: Long = 0): String
    fun kanbanCreate(board: String?, status: String): String
    fun kanbanEdit(taskId: String, board: String): String
    fun kanbanLog(taskId: String, board: String): String
    const val KANBAN_BOARD_NEW = "kanban/board/new"
    fun kanbanBoardSettings(board: String): String
}
```

- The create route is `kanban/new?board=…&status=…` (not `kanban/task/new`;
  avoid the `{taskId}` collision).
- The detail route is `kanban/task/{taskId}?board=…&cursor=…`.
- The edit route is `kanban/task/{taskId}/edit?board=…`.
- The log route is `kanban/task/{taskId}/log?board=…`.
- The board settings route is `kanban/board/{slug}/settings`.
- `cursor` is a `Long`; `0` means "no cursor, poll instead of SSE".
- Encode task ids and slugs with `Uri.encode`. Board slugs and task ids are safe
  today; do not rely on that.

data class KanbanFilters(
    val assignee: String? = null,
    val onlyMine: Boolean = false,
    val tenant: String? = null,
    val includeArchived: Boolean = false,

wires the board's card tap. The create screen (Task 22) fills the board's FAB and
the board's create-result integration. Do not ship a phase with a dead card/FAB:
if executing strictly phase-by-phase, keep the board's `onCreateTask` null and
the card tap deferred until the destination exists.

## Deliberate implementation choices (not in the design, or narrower)

- **Move-sheet parent check** fetches the task detail when the sheet opens,
  because the board payload has only `link_counts` (no parent ids). This is one
  extra read for an occasional action; it is what makes the Ready gate honest.
  The detail already has links, so it uses the shared cache directly.
- **Workspace picker** lists saved workspaces and accepts a typed path; it does
  not call `/workspaces/add`. Task creation passes `workspace_path` through. If
  the user needs to register a new workspace first, they can do that in the
  existing Spaces panel. This avoids coupling the editor to the composer's
  workspace typeahead.
- **No `render_markdown` branch**: the app always renders the Markdown it
  already supports. The config field is a WebUI display preference; hiding
  Markdown would lose task formatting.
- **No bulk multi-select** in v1; the bridge supports it, but the design defers
  it to Phase 5 and this plan does not require it.
- **Task picker fetches the full unfiltered board** on every open, as the design
  requires; it is not cached across opens.
- **The dispatcher result is `JsonObject`**, not a DTO, so a newer server's
  bucket appears instead of being dropped.
- **Board archive is optimistic**; the open detail's archive waits for the
  server and then pops (the design requires the pop). The detail does not surface
  an Undo snackbar that would die with the screen; the board's archive path
  offers Undo. This is the one place where §9.4's optimistic archive is
  board-only.
- **The detail's archive Undo** is therefore not offered; use Restore/Reopen
  after the task leaves the board. The board's archive Undo remains the quick
  reversal.
- **The board's created-task result** rides `SavedStateHandle` keys
  (`created_task_id`, `created_task_status`, `created_requested_status`,
  `created_unreadable`, `created_follow_up_error`) from the create destination
  to the board destination.
  This is the Navigation Compose result mechanism, not a new event bus.
- **The edit screen never edits status**; status changes go through the
  detail's workflow actions. This avoids the WebUI's "actual status" confusion.
- **Create defaults to Ready**; the board's FAB passes the selected status, but
  running/blocked/done/archived are sanitized to triage before the form opens.
